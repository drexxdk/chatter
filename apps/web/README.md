# Chatter — Web Client

The end-user chat client: a lobby of public rooms, a nickname prompt, and the chat room itself. Built with React, Vite, Tailwind CSS and react-i18next (English, Danish, German). It talks to `apps/chat-server` only; it never calls the admin app.

## Local setup

1. Start the backend: Postgres/Redis (`docker compose up -d`), `apps/admin` and `apps/chat-server` (see their READMEs).
2. Optional: `cp .env.example .env` if chat-server isn't at `http://localhost:4000`.
3. From the repo root: `npm run dev:web`, then open http://localhost:5173. The port is fixed because chat-server only allows that origin through CORS (`WEB_ORIGIN`).

## How it works

- `src/chat/useChat.ts` owns the Socket.IO connection and turns the chat-server protocol (documented in `apps/chat-server/README.md`) into React state: session, current room, members, messages and error code. What does not need the hook's state is next to it: `types.ts` (the shapes), `messages.ts` (reading what the server sends, merging history, redaction) and `reconnect.ts` (delays and which errors are final).
- Guests are anonymous: a nickname is the only input. Nickname rules are mirrored in `src/nickname.ts` for instant feedback; the server stays authoritative.
- Messages are rendered as plain text, never HTML.
- **Room search:** the header textbox searches loaded room messages and the guest's private messages shown in the room timeline by text or sender. Results appear only for a nonempty query; image attachment URLs are excluded from matching and previews. Result previews follow the chat: the guest's messages sit on the right, private messages use yellow with a dashed border, and moderators keep their green styling. Ctrl+F / Cmd+F focuses the field; arrows and Enter select a result and reveal the original message. Escape or clicking outside closes the results. Hidden or banned content is excluded. Search resets when changing rooms and uses retained client history, not an archive of older messages.
- A dropped connection (network loss, ping timeout) while in a room is recovered automatically: the room stays on screen with a "Reconnecting…" banner and sending paused, the client connects again with the same nickname and rejoins the room. It retries for about four minutes (1s, 2s, 4s, 8s, 15s, 15s, then every 30s) and tries at once when the browser reports it is back online or the guest returns to the tab, since a background tab's timers are slowed down. A new connection takes over the identity of the old one (the client presents its guest id and the secret the server gave it, see "Resuming an identity" in the chat-server README), so other guests see the member leave and come back but it is the same person; if the server does not accept it, the guest gets a new id and the hook still remembers all of its own ids to keep earlier messages recognisable as theirs. It gives up after the last attempt (`connection_lost`), stops at once on a ban or invalid nickname, and does not retry when the server disconnects the guest on purpose (inactivity kick) or when the guest was only browsing the lobby. Messages sent while disconnected are not delivered afterwards, because the server keeps no history.
- Routing is `react-router` (`BrowserRouter` in `main.tsx`: `/auth/callback` is a page of its own and everything else is `App`). `App` shows the lobby, a room, or one of `/terms`, `/privacy` and `/about` under one header (the profile button, once somebody is connected or signed in, and the menu are the same everywhere; there is no login button, a guest is asked who they are when they join a room), and `ViewTransition` slides between them: forwards when the new view is deeper than the one it replaces (the lobby is the top, all else a step down), backwards when it is shallower, so the back button and the site title slide back to the lobby. The address shows the room (`/rooms/<slug>`): entering a room adds a history entry and leaving adds another, so the back button leaves the room and forward goes in again. After a reload, or when a room's address is opened, the client rejoins as the guest this tab already was (nickname, avatar and, for a moderator, the signed token, never the password; kept in session storage, so per tab, and forgotten when the connection ends for good), or asks who they are if the tab has none. Private conversations (and who was blocked) are kept in the tab too, under their own key, so a reload does not empty them; the conversation that was open is open again if the other person is still in the room, and otherwise the room is shown and the conversation stays in the list. After such a return, each conversation says that the guest left and came back, just as it does for the other person. An unknown room goes to the lobby. **Hosting:** because of this, whatever serves the built app must answer unknown paths with `index.html` (the Vite dev and preview servers already do).
- Direct messages, avatars and moderators are described in `apps/chat-server/README.md`. Messages sit in bubbles (what others say on the left with their avatar, the guest's own on the right); a conversation also shows when the other person left the room or came back, as a blue line with the time. How each avatar looks is defined in one place, `src/components/Avatar.tsx`.
- The room's log also says, as blue lines with the time, who came into the room and who left it. They are worked out from the changes in the member list (the server sends no events), put between the messages in the order they arrived, and shown while "Show when people join and leave" is ticked (on to begin with; the choice is kept in the browser, `localStorage`). They are recorded either way, so ticking the box shows what happened meanwhile. They are not kept across a reload, and nothing is shown about a guest who was banned. See `src/chat/roomEvents.ts`.
- **Attachments**: the plus button at the start of the message box opens a left-aligned panel above it, with a desktop-only Emoji tab (emoji-mart's picker, `src/components/EmojiPane.tsx`: the sections are tabs along the bottom, the one in view marked and a click scrolling to its section, with a search and the ones used most often first; its words come from `picker.mart` in the locales, its styles from `em-emoji-picker` in `src/index.css`, and its data, a large file, is fetched when the tab is first opened; it has its own keyboard handling), a YouTube tab and, when there is a GIPHY key, a GIFs tab. Touch devices omit the Emoji tab because their keyboards already provide emoji. Emoji and GIFs are inserted at the cursor. A GIF is an atomic TipTap node inside the message box (`src/components/AttachedGif.tsx`), with editable text above and below it, a remove button, keyboard deletion, and undo/redo. Send preserves that order (`src/chat/useComposer.ts`). The GIFs come from GIPHY. GIPHY requires searches to be made from the browser, so the client calls `api.giphy.com` itself with a public API key from `VITE_GIPHY_API_KEY` (create one at https://developers.giphy.com/dashboard); without the key the panel still offers YouTube and, on desktop, Emoji. Results are limited to rating `g`. Each GIF is sent as its address on a separate line in an ordinary text message (`https://media*.giphy.com/media/.../*.gif`, without GIPHY's tracking query), so the chat-server, history, slow mode, bans and private conversations need no changes. Trusted GIF lines are rendered as pictures in their original position among the words (see `src/chat/gifs.ts`). The picture is played as the video GIPHY serves at the same address with `.mp4` instead of `.gif`, because a GIF's own loops cannot be controlled: it plays once when it first comes into view (not at all for somebody who prefers reduced motion), then waits with a play button; that plays it again in a loop until the Stop button is pressed (`src/components/GifImage.tsx`). The preview of a GIF added to the message being written is a still, and if the video cannot be loaded the GIF is shown as the picture it is; unrecognised addresses stay text. Addresses and their separating line breaks count towards the 500 characters, so adding a GIF shortens the room left for words. Viewers' browsers fetch the pictures from GIPHY, which therefore sees their IP address. The pickers that open from the message box (emoji and GIFs, who to write to) and the reaction grid are dialogs like the header's menus: the page does not scroll while one is open, the cursor starts in its search box, Down goes from the search box into the grid, the arrow keys, Home and End move between the items (`src/gridNavigation.ts`, which finds the neighbour by where the items are on the screen), Tab leaves the grid after one stop, and Escape closes it and returns to the button.
- **YouTube**: the YouTube tab previews a pasted watch, share (`youtu.be`), Shorts, live or embed link using its thumbnail from `i.ytimg.com`, so previews do not depend on embedded playback working in the browser. Insert adds a video at the cursor without sending. Video attachments support removal, keyboard deletion and undo/redo, and count towards the message length limit. Only allowlisted YouTube hosts and 11-character video IDs are accepted (`src/chat/youtube.ts`); URLs are normalized to `https://www.youtube.com/watch?v=...` without tracking parameters. The URL travels as a separate line of an ordinary message, preserving surrounding text in rooms and private messages. The player uses `www.youtube-nocookie.com`, does not autoplay, and sends the viewer's IP and referring origin to YouTube when loaded. Thumbnail requests also expose the viewer's IP to YouTube, but send no referrer. Link validation does not guarantee that a video exists or permits embedding; the player handles unavailable, private or restricted videos. No YouTube API key is required. Production CSP permits frames only from this privacy-enhanced YouTube host and preview images from `i.ytimg.com`.
- **Message box and mentions**: the box is a TipTap editor (`src/components/MessageInput.tsx`) holding one paragraph with line breaks, so that what is in it is what is sent (`src/chat/plainText.ts`, reported to `useComposer`). Enter sends and Shift+Enter starts a new line (on a touch screen Enter starts a new line); paste is plain words, cut to what fits; nothing is accepted beyond 500 characters. An "@" at the start or after a space or line break opens a list of the other people in the room (not those the guest has blocked), narrowed as the name is written, which may have spaces in it; arrows move, Enter or Tab chooses, Escape closes. A person chosen is a name in colour, without the "@", that Backspace removes whole and that goes out as `@Name`. In messages, `@Name` of somebody in the room (matched ignoring case, at the start or after whitespace) is shown as the name alone in the same colour, with a card (name, gender, age) on hover and a click that chooses them to write to (`src/chat/mentions.ts`, `src/components/Mentions.tsx`; the card is placed with `@floating-ui/react`).
- **Profile and menu.** The header menu opens from the guest's avatar and offers their profile (nickname, avatar, age; a moderator's name comes from their account), the setting for showing who comes and goes, and the language. Age is optional (18 to 99, digits only) and, like the avatar, shown to everybody in the room: the client sends it in the handshake, changes go through `profile:update` (see the chat-server README), and a reload brings the guest back as they changed themselves to (`rememberProfile` in `src/session.ts`). The room's people list shows it next to the name; conversations follow a guest who renames themselves.
- A nickname somebody else in the room has is refused (`nickname_taken`): joining then keeps the nickname dialog open with the reason so the guest can pick another, a reload that finds its name taken asks again, and the profile modal shows the error when renaming.
- What somebody writes one message after another, with nothing in between (nobody else's message, nobody coming or going), is shown as one group: their name once, the time of the last message, and each message in its own bubble (`src/chat/runs.ts`, `MessageGroup` in `src/components/MessageRow.tsx`). Clicking a message in the room chooses its author to write to privately, as choosing them in the people panel does (the panel is beside the messages on a wide screen; on a narrow one the "People" button above the message box slides it in between the header and the box, next to the line that says who is being written to) (not for the guest's own messages, nor for somebody who has left or is blocked); a click never opens a menu. What can be done with the person (write to them, open the private chat, block or unblock them) is in the "…" button at the end of the bar that shows when a message is hovered, held on a touch screen, or focused (the menu key or Shift+F10 opens it from the keyboard; `src/components/PersonMenu.tsx`); it is on other people's messages and on private messages in the room's log, not on the guest's own. Somebody who has left the room is marked with a dimmed avatar and a "Left the room" note under their messages (not beside the time, which is when the message was sent), which stay; they cannot be written to, and the private chat with them can only be opened from the menu if the two have written to each other before. In a private conversation a click does nothing. Every message is one stop in the list, which is a single Tab stop. The keyboard follows three rules everywhere: Tab moves between areas of the page; the arrow keys move around inside one (up and down always change message; left and right always walk along what can be done with the message in focus: the bar's quick emoji, the full set and the options menu, then a GIF's play or stop button, then the reactions under it); Enter or Space does or opens, and Escape goes back one step (from a menu or panel to the button that opened it, from that button to the message, and from the message box to the messages). Enter on a message chooses the person to write to. R, P and the menu key are shortcuts for the full set, a GIF and the menu, but nothing needs them (`src/messageKeys.ts`, `src/rowNavigation.ts`).
- Messages in a room can be reacted to, as in Teams (`src/components/MessageEntry.tsx`, `src/chat/reactions.ts`): hovering or focusing a message shows a bar with four quick emoji and a button for the full set; under the message each emoji it has been given shows with how many reacted (the guest's own are highlighted, the title lists who), a click joins or leaves, and a small button beside them adds another. With a message focused by the arrow keys, R opens the full set. On touch screens, holding a message shows the quick reactions (a short tap still chooses the person). A guest's own messages show what others added but cannot be reacted to by their author. The choice is limited to a fixed set the server also checks; reactions on private messages work the same way, but are kept only by the two clients (`dm:react`, `src/chat/direct.ts`).
- When the page is scrolled up from the newest message, a round arrow button shows in the bottom left corner of the message window, just above the message bar; it scrolls back to the end (`src/components/ScrollToEnd.tsx`).
- Times next to messages read "a few seconds ago" and "N minutes ago" for the first 15 minutes, then show the time of day, on a 12-hour clock with AM and PM only where that is what the guest's locale uses (Dansk and Deutsch are 24-hour; for English a European or African time zone, or an English locale of a 24-hour country such as en-DK or en-GB among the browser's languages, means 24-hour; see `src/chat/clock.ts`); they update by themselves (`src/components/Timestamp.tsx`).
- Server error codes are translated in `src/locales/*.json` under `errors.*`. Adding a new code on the server needs a key in all three files; `src/locales.test.ts` enforces that the locales stay in sync.
- **Reporting.** Another person's message has "Report message" in the same "…" menu (not the guest's own, not a moderator's, and not private messages: those are not stored on the server, so there is nothing to judge). A dialog asks why (`src/components/ReportDialog.tsx`), `useChat.reportMessage` emits `message:report` (see the chat-server README, "Reports"), and on success the message turns into a placeholder for the guest at once ("Message hidden after being reported"). When enough people have reported it the server says so with `message:hidden` and it becomes the same placeholder for everybody; a placeholder like that also comes in the history of a room joined later (`hidden: true`, parsed in `src/chat/messages.ts`).
- **Terms and age.** The terms of use and the privacy policy are views of the app at `/terms` and `/privacy` (`src/components/LegalPage.tsx`, shown by `App` in place of the lobby), in the guest's language, linked from the lobby and nickname dialog. They keep the site's header (`HeaderFrame`, with the menu that sets the language) and show a breadcrumb back to the lobby. Their text is not in this app: it is written in the admin (**Terms and privacy**), served by the chat-server's `GET /legal` and fetched by `useLegal` (`src/legal/`, which also validates the shape; a page that cannot be shown whole says so and offers a retry). `VITE_CONTACT_EMAIL` (default in `src/config.ts`) is only the address shown when the text could not be loaded; the one in the text is the admin's. A guest joining as a guest, in a browser that has not accepted the current version, has to tick "I am 18 or older and accept the terms of use and the privacy policy" in the nickname dialog (the links open in a new tab, so nothing typed is lost); the browser remembers the version it accepted in local storage (`chatter.terms`) and later shows the box already ticked (it can be unticked, and then the guest is not let in). The admin's "terms version" is the version: change it when the documents change in a way that matters and everybody is asked again (while the version is not known, a browser that has accepted anything is not asked). There is no way to check an age, so this is the user's statement and the terms' rule; moderators signing in are not asked.
- **Accounts.** A guest can connect Google, Facebook or Discord (the chat-server says which are on, `GET /auth/providers`, and nothing is shown when none is). The buttons are in the nickname dialog (\"Or continue with an account\"), in the profile of a guest in a room, and, being in the nickname dialog, they are what a guest sees when joining a room; they come back to that room, where somebody who has an account is let in as the account, without being asked who they are. Each button is a link: the browser leaves for the chat-server, then the provider, and comes back to `/auth/callback` (`src/components/AuthCallback.tsx`) with the outcome after the `#`, which the page takes out of the address at once. Somebody who already has an account is signed in; somebody new fills in a form on that page: a **username** (no spaces; they cannot be typed, it is never shown in the chat), a **display name** (what the chat shows; a run of spaces is made one when it is sent, `tidyName` in `src/nickname.ts`), an **avatar** picture, the optional gender and age, and the terms. A guest who connects a provider starts from who they were (their nickname as the display name, a username made from it, their gender and age). The avatar picture is one of eight drawn with DiceBear (`@dicebear/core` and the style files of `@dicebear/styles`, fetched on first use, `src/chat/pictureImage.ts`; the styles are the CC0 ones listed in `src/chat/picture.ts`, which must match the chat-server), chosen at random by default and always one; the button beside them brings other ones. Only the style and the seed (`lorelei:k3j9x2ab`) are kept and sent. In a room, everybody's picture is where the symbol of their avatar was, and the symbol goes beside their name (`GenderMark` in `src/components/Avatar.tsx`). Guests choose one too, in the nickname dialog (the same eight to choose from, one picked at random, sent in the handshake and kept in the tab's session for a reload) and can change it in their profile; a moderator has none, so they keep the symbol. The account (a signed token, 30 days, renewed at every page load by `GET /me`) is kept in local storage (`src/account.ts`); a signed-in person joins a room without a nickname dialog, and the profile in a room can change the display name and the picture, and has **Sign out** and **Delete my account**. In a room they have the role `member`, with the same rules as a guest. `src/test/fakeSocket.ts` treats a token that starts with `member-` as an account's, and `src/test/setup.ts` stands in for drawing a picture.

## Reload state and private drafts

The URL keeps non-sensitive UI flags for sign-in, guest room entry, profile viewing/editing, account creation, notification settings, header menus, chat search, the attachment picker and its selected tab, and the mobile people panel. UI changes replace the current history entry; they do not add entries for opening a menu or typing. Initial load restores available UI after room/session restoration. Back/Forward navigates between pages and rooms without replaying old UI flags, and removes those flags from the visited entry.

Textbox contents are not URL parameters. Message drafts (including attachments and mentions), room/people searches, picker inputs, sign-in identifiers, guest nicknames, and unsaved profile fields use bounded `sessionStorage` entries under `chatter.draft.*`. Entries expire after eight hours, are cleared on sign-out/session cleanup or authentication-token changes, and tolerate unavailable or malformed storage. Room and conversation message drafts are isolated; an inline private draft is restored only with its validated recipient, never silently as a public message. Sending clears its draft; saving or cancelling profile editing clears its unsaved fields. Passwords are never persisted by this feature. Existing saved account preferences and accepted terms retain their existing storage.

Unknown or unavailable UI flags are removed. Confirmed nonexistent rooms return to the lobby, but a room-list network failure retains the intended address for retry. Restoring UI never sends messages, submits forms, accepts terms, or performs moderation/account actions. Message-specific reaction/action popups and destructive confirmation dialogs remain transient. No new cookies or database fields are used.

`src/reloadUi.tsx` owns URL synchronization, `src/components/ReloadMenu.tsx` coordinates accessible dropdown/popover lifecycles, and `src/tabDraft.ts` owns private draft storage. Generated Playwright reports and test results are excluded from Vite watching so report generation cannot reload or crash a running development session.

## Docker and the content security policy

`apps/web/Dockerfile` builds the client and serves it with nginx (as a non-root user, on port 8080; a room's address falls back to `index.html`). Build from the repository root:

```sh
docker build -f apps/web/Dockerfile --build-arg VITE_CHAT_SERVER_URL=https://chat.example.com -t chatter-web .
docker run -p 8080:8080 -e CHAT_SERVER_SOURCES="https://chat.example.com wss://chat.example.com" chatter-web
```

The chat-server's address is part of the build (`VITE_CHAT_SERVER_URL`, and `VITE_GIPHY_API_KEY` for GIFs). `CHAT_SERVER_SOURCES` goes into the `Content-Security-Policy` header (`nginx.conf.template`) as the places the page may connect to besides itself and `api.giphy.com`: the chat-server's `https` address (the room list and the moderator sign-in) and its `wss` address (the socket). The policy allows scripts only from the page's own files, pictures and video only from GIPHY, and no framing, so injected markup could not run code or send anything elsewhere. The chat-server's `WEB_ORIGIN` must be the address this page is served from.

The Vite dev server sends no such policy; if you add a source the page loads from (another image host, a font, an analytics script), add it to `nginx.conf.template` too, or the browser will refuse it in production and only there.

## Tests

`npm run test:web` (Vitest + Testing Library). The tests run the real components, hook and i18n against a fake Socket.IO server (`src/test/fakeSocket.ts`) that replays the real protocol, including the server's event ordering. No network or running backend is needed. If the chat-server protocol changes, update the fake to match.

Vitest uses at most two workers and does not retry failed tests. Wait for the intended input to receive focus before typing in a newly opened dialog; a visible dialog alone does not mean its focus transition is complete.

`npm run lint --workspace apps/web` runs ESLint (`eslint.config.mjs`): the recommended TypeScript rules plus `react-hooks/rules-of-hooks` and `exhaustive-deps`, both as errors, and `no-deprecated` (type-aware, so it also flags React and DOM APIs marked deprecated, such as `FormEvent`), and CI runs it. Where an effect deliberately leaves out a dependency (two places in `App.tsx`), the line above says why.

### End-to-end

`npm run test:web:e2e` (Playwright) drives a real browser against the real chat-server. It covers two guests chatting (including HTML shown as text), a guest whose WebSocket is cut being reconnected to the same room, a full room turning a guest away, and a ban blocking the connection until it is lifted.

- Requires `apps/admin` running on http://localhost:3000 with its database seeded, plus Postgres and Redis (`docker compose up -d`). Everything else is started by the tests.
- It runs its own chat-server (port 4100) and web client (port 5174), so a dev session can stay open. The e2e chat-server uses Redis database 1, its own Socket.IO channel (`SOCKET_ADAPTER_KEY`), its own ban salt and a 500ms cache sync.
- It creates rooms prefixed `e2e-` and bans through the admin API and removes them afterwards; leftovers from an interrupted run are swept at the start of the next one. It reads the admin credentials from `apps/admin/.env`.
- The ban test blocks loopback addresses for the e2e chat-server, so tests run one at a time.
- Scroll and layout regressions use fresh rooms per attempt so existing history, late-loading media and retries cannot alter their fixtures. Click visible controls instead of forcing clicks on hidden inputs.
- Failure screenshots and traces are retained from the first attempt, including when a CI retry passes. To check stability without retries, use `npm run test:web:e2e -- --retries 0`; repeat a targeted test with `--repeat-each 3 -g "test name"`.
