- Message history (`apps/chat-server/src/history.ts`, `useChat.ts` on the web side): every message is appended to a per-room Redis list (newest `ROOM_HISTORY_SIZE`, default 50, at most 200; expires `ROOM_HISTORY_TTL_SECONDS` after the last message, default 1 hour, at most 7 days) in one transaction, before it is delivered live. The `room:join` ack now carries the room's history, read after the guest has joined, so nothing sent in between is missed; the web client merges it by message id (no duplicates, sorted by time, other rooms ignored), which also covers messages missed during a reconnect. A Redis failure costs only the history entry, never the live message, and an unreadable history never blocks a join. Entries are validated with Zod when read. Written test-first (history module, socket and client tests, a reconnect scenario in the real-browser suite: 147 chat-server, 59 web, 6 e2e tests pass); 10 deliberate bugs were tried and 9 caught (the tenth, throwing inside the reader's own try block, is an equivalent change). - Bans now reach guests who are already connected and what they said (`enforceBans` in `socket.ts`, wired in `index.ts` through `startBansSync`; `redactMessagesFrom` in `history.ts`). Found while designing this: a banned guest who was already connected kept chatting, because bans were only checked at connection time. After every ban sync (all active bans, so it also heals races): connected banned guests of the node are sent `kicked { reason: "banned" }` and disconnected; in every room the history entries from the banned IP hashes are replaced, in one Lua script inside Redis, by placeholders with no text, nickname or guest id; the room gets `message:redacted { roomSlug, ids, guestIds }` and clients swap those messages for a red "This user was banned" (en/da/de), including older messages by the same guest that the history no longer holds. History entries now carry the sender's IP hash (server only, never sent to clients; entries from before this change have none and are not shown). A message still being recorded when the ban lands is dropped and redacted. On the client a placeholder in the history overrides a live copy, and live duplicates are ignored by id. Written test-first (chat-server 173 tests, web 74 tests, 7 real-browser scenarios including one where a banned guest is removed while another watches her message turn into the placeholder on screen, and a later joiner never sees the text); 16 deliberate bugs were tried and 15 caught (the survivor, a redundant exclusion of the removed guest from the notice, was removed instead); the Lua script was also run against a real Redis (order, expiry, nothing left behind, idempotent, tolerates a corrupt entry). Limits: up to one sync interval of delay (30 s by default); a replaced message stays replaced after a temporary ban expires; the stored hash is a salted IP hash, so someone with the salt could test an address against it, but cannot read addresses from it.
- Slow mode (phase 1 of user types and moderation): each room has a `slowModeSeconds` field in Payload (whole number of 1 or more, default 10 for new rooms, validated in Payload because the chat-server rejects a rooms response it cannot read; migration `add_room_slow_mode` gives existing rooms 10 through the column default). Guests wait that many seconds between messages, counted per connection across rooms (so hopping between rooms is no way round it) and refused attempts do not extend the wait; the answer is `rate_limited` with `retryAfterMs`, and the room's setting is read per message so a change applies at once to people already inside. A room with the field empty gets the chat server's default (`DEFAULT_SLOW_MODE_SECONDS`, 10 unless configured, never off) instead of being unlimited, and `/rooms` always shows the number in force. This replaced an earlier choice where an empty field meant only the general flood limit (5 messages per 5 seconds); the e2e server sets the default to 1 second so the tests are not slowed. The client shows \"Slow mode: one message every N s.\" under the room name and, when refused, \"You can send again in N s.\" (rounded up; en/da/de). Two messages sent back to back cannot both pass the check (it is synchronous after the room lookup). Written test-first (186 chat-server tests, 78 web tests, 8 browser scenarios including one with a 3-second room); 8 deliberate bugs were tried and the 7 that applied were caught. At one message per 10 seconds, 1000 guests send at most about 100 messages per second, a tenth of the earlier worst case. Next phases: roles and moderator sign-in, then announcements. Also fixed along the way: the e2e Payload login now times out after 30 seconds instead of hanging when the admin app is wedged.
- Moderators (phase 2 of user types and moderation): chat users now have a role, `guest` or `moderator`, assigned only by the server; what each role may do lives in one table (`ROLE_RULES` in `roles.ts`), so a later role is a new row. A moderator is a Payload `admins` account with role `moderator` (no admin panel access) or `super-admin`, plus a unique `displayName` (migration `add_moderator_role`). They sign in from the nickname dialog with their email and password: the chat server forwards them to Payload's login (rate limited to 10 per 15 minutes per IP, body capped at 2 KB, password never stored or logged) and answers with an HMAC-signed token (8 hours, `AUTH_TOKEN_SECRET`, optional; without it sign-in is off) that holds only id, name, role and expiry. The socket takes the token instead of a nickname and the name always comes from the account; the client keeps the token so a dropped connection reconnects without asking again, and an expired one sends the person back to the lobby with a clear message. Guests cannot take a moderator's name (compared ignoring case, spacing and punctuation) or names such as Admin, Staff, Support, System or exactly Mod; the list is synced into Redis. Moderators ignore IP bans (their stored history copy carries no IP hash, and `enforceBans` skips them) but follow the same slow mode and flood limit. Messages and the member list show a moderator's name in bold green, with a "Moderator" badge and bold green text (en/da/de); the role comes from the server, so a guest calling themselves "Moderator" looks like any guest. Written test-first (chat-server 314 tests, web 85 in `App.test.tsx`, 10 browser scenarios including a real moderator account created through Payload); 34 deliberate bugs were tried and 32 caught at first. Of the two survivors, one showed a weak ban test (fixed and re-checked) and the other a line that did nothing (removed). Limits: there are no direct messages yet. (Two limits listed earlier were then removed, see the next entry.)
- Moderator access follow-ups: removing a moderator in Payload now takes effect within one sync interval instead of when their 8-hour token expires. The chat server caches the moderating accounts (id and name) in Redis (`chatter:moderators`, replacing `chatter:moderator-names`), refuses a token whose account is not in the list, and after every sync disconnects connected moderators who are no longer in it (`kicked { reason: "invalid_token" }`, shown by the web client as "Your moderator session has expired"). A list that was never read, or Redis being unreachable, fails closed. Signing in records the account in the list at once so a brand-new moderator is not refused before the next sync (the sync stays the authority). Moderators also no longer count toward `MAX_CONNECTIONS_PER_IP` (a new `ignoresConnectionCap` rule in `ROLE_RULES`), so they can still moderate while guests fill the limit. Written test-first (chat-server 374 tests, 105 in web `App.test.tsx`, 13 browser scenarios including one where the account is deleted while the moderator is chatting).
- Announcements (phase 3 of user types and moderation): a moderator can tell everyone connected something (`announce:send`, 1 to 500 characters, once a minute per account). The wait is a Redis key taken atomically (`SET NX PX`), so a second connection or node is no way round it, and a refused text does not use up the turn. The server answers every connection with `announcement:new { id, text, sentAt, name }` (through the Socket.IO adapter, so on every node), keeps only the latest in Redis for an hour and sends it right after `session`, so someone arriving later sees it. It is delivered live even if it cannot be kept, and nobody is stopped from connecting if it cannot be read. Not part of any room history. The web client shows a green, bold banner with the moderator's name and a Dismiss button, in the lobby and in a room; a dismissed one does not return when the server repeats it after a reconnect, a newer one does; moderators get an announce box under the message box that keeps the words and explains how long to wait when refused (en/da/de). Written test-first (chat-server 347 tests, web 104 in `App.test.tsx`, 12 browser scenarios including a moderator, a guest who arrives later, the wait and dismissing); 22 deliberate bugs were tried and 21 caught at first (one test gap found and closed, two edits that did not apply were re-run, and one survivor is an unreachable check: only moderators have accounts, so the role flag and the account check cannot disagree yet). Along the way: an empty room slow mode now means the server default of 10 seconds (`DEFAULT_SLOW_MODE_SECONDS`), not only the flood limit, and e2e now clears the previous run's room history and announcement, which had been skewing counts.
- Direct messages, avatars and reload-proof sessions (written test-first; chat-server 452 tests, web 311, 19 browser scenarios):
  - Direct messages: a guest writes privately to someone in the same room (`dm:send` / `dm:new`, echoed to the sender), nothing stored on the server. Blocking (`dm:block` / `dm:unblock`, silent to the sender, at most 100, moderators cannot be blocked through `blockable` in `ROLE_RULES`). Shares the flood limit with room messages, and starting conversations with new people is limited to 5 per minute. A banned author's messages become placeholders in conversations too.
  - Avatars: `male`, `female`, `trans`, `other` (self-declared, unknown becomes `other`, moderators always `other`), sent in session, presence, messages, history and direct messages. Messages are bubbles (others left with their avatar, the guest's right); the people list shows everybody including the guest ("you"); a conversation shows blue status lines when the other person left or came back.
  - The address shows the room (`/rooms/<slug>`) with working back and forward; a reload or opened address rejoins as the same tab's guest. Session storage keeps the nickname, avatar, moderator token (never the password), the guest ids used so far, the resume secret, and the private conversations, who was blocked and which conversation was open. The conversation is open again only if the other person is still in the room. Hosting needs an SPA fallback (unknown paths answer `index.html`).
  - Resuming an identity: each connection gets a secret (`session.resumeSecret`, rotated per connection, only a SHA-256 in Redis for an hour under `chatter:resume:<guestId>`, compared in constant time). A new connection that presents the id and secret takes the same `guestId`, the old one gets `kicked { reason: "replaced" }`. So after a reload the other person sees the guest leave and come back, can keep writing, and both sides' copies of the conversation say the same. Wrong or missing secrets simply give a new identity.
  - Reconnecting now retries for about four minutes and at once when the browser comes back online or the tab is shown. The rooms list limit is configurable (`ROOMS_RATE_LIMIT_PER_MINUTE`, default 60; the e2e server raises it because every test opens the lobby from one address).
  - The room log announces who joins and leaves (worked out from member list changes, shown while a checkbox is ticked, the choice kept in `localStorage`; not shown for banned guests; not kept across a reload).
  - Mutation checking: on the server, avatar changes were all caught, and resume checks were all caught except that the secret was not rotated, which got a test. On the web, about 55 deliberate bugs were run against the first version of the resume and persistence code; the survivors showed missing tests for what is saved and read back (empty ids and secrets, caps of 20 ids and 100 blocked ids, token type, the open conversation, not reviving a forgotten session), now covered by `session.test.ts` and `App.test.tsx`. Three survivors were redundant code and not observable: a reset of the resume secret (removed) and two resets of conversations and blocked ids when a connection ends (kept as cleanup, since the next connection overwrites them anyway). The run was stopped at about half, and the code written after it (room announcements, the restored conversation, own status lines) has not been mutation-checked yet.
  - Limits: direct messages exist only for guests while the tab lives (kept for members is planned: registered members via Google/Facebook, then conversations kept for 30 days in Postgres); the secret only proves "same guest", bans and caps still apply on every connection.

### Not yet done

- `apps/chat-server` socket logic still missing: capacity enforcement across multiple nodes (joins to limited rooms are serialized per room by an in-process lock and the per-IP connection cap is counted per process; a Redis-side counter is needed before running more than one instance).
- Presence cost: every join, leave and disconnect sends the full member list to everyone in the room, so traffic grows roughly with the square of the room size. Fine for small rooms; very large or unlimited rooms need counts or deltas instead.
- Payload schema changes are applied by dev-mode push only; there are no migrations yet, so the `maxMembers` change (now optional) needs a migration before any real deployment.
- `apps/web` gaps: no typing/unread indicators, no mobile-specific layout work beyond Tailwind defaults.

### Environment notes

Findings were checked against the code; things the review claimed that turned out to be wrong are not listed. Worked through in this order; `[x]` means done.

### High value

- [x] 1. Real-Redis tests for the Lua scripts in `apps/chat-server/src/history.ts` (`REACT_SCRIPT`, `REPLACE_SCRIPT`): every test mocked Redis, so the ban redaction and reaction toggling were only ever checked by hand. Now `src/history.redis.test.ts` (13 tests: order and trimming, expiry kept, toggling on and off, the limits, own and missing messages, banned placeholders, non-ASCII text, concurrent reactions) runs against a real Redis when `TEST_REDIS_URL` is set; CI has a Redis service container for it.

- [x] 3. Graceful shutdown (`src/shutdown.ts`, wired in `index.ts`): on SIGTERM/SIGINT the syncs stop, clients are disconnected, the HTTP server closes and the three Redis connections quit, with a 10 s fallback and exit code 1 on failure. Unit-tested, and checked for real: `docker stop` on the container logs the shutdown and exits 0 in under half a second.
- [x] 4. ESLint for `apps/web` (recommended TypeScript rules, `rules-of-hooks` and `exhaustive-deps` as errors) and `apps/chat-server` (recommended TypeScript rules); both have a `lint` script, so CI's `npm run lint` covers them.
