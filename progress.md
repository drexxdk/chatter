- Reconnection in `apps/web` (`src/chat/useChat.ts`): when the connection drops unexpectedly while the guest is in a room, the room stays on screen with a "Reconnecting…" banner and sending disabled, the client opens a new connection with the same nickname (backoff 1s, 2s, 4s, 8s, 15s; configurable for tests) and rejoins the room. It does not use Socket.IO's built-in reconnect, because the server gives every connection a new guest id and a reconnect would not rejoin the room. It stops at once on a ban or invalid nickname, gives up after the last attempt with a translated `connection_lost` error, ignores deliberate disconnects (inactivity kick, own disconnect), does nothing for guests who were only in the lobby, lets the guest leave while reconnecting, and stops on unmount. The hook remembers all of the guest's ids so earlier messages stay highlighted as theirs.

- Room limits are now optional and the server is protected per IP instead (decided after discussing whether a per-room cap is needed: its real value is a product choice, while server protection belongs in a connection cap):
  - `PublicRooms.maxMembers` is optional in Payload (empty means unlimited; the old default of 50 and the required flag were removed; existing rooms keep their numbers). The chat-server skips the cluster-wide member lookup for unlimited rooms, and the lobby shows no capacity line for them.
  - Per-IP connection cap in the chat-server (`MAX_CONNECTIONS_PER_IP`; unset means no cap, `.env.example` ships `10`, and any value that is not a positive whole number, including `0`, stops the server at startup so a typo cannot silently disable it): over-limit connections get `too_many_connections`, which the web client translates and, during a reconnect, keeps retrying through (the guest's own dropped connection may still be counted for a while). The slot is reserved synchronously after the async ban check and only if the client is still connected, because a guest who leaves during that check never triggers a `connection` event and would otherwise leak the slot; released on disconnect.
  - Client IP resolution (`getClientIp`, `TRUST_PROXY_HOPS`, default 0): the `X-Forwarded-For` header is ignored unless you say how many of your own proxies sit in front, and then only the entry those proxies appended is used (client-supplied entries to its left are ignored). This applies to both bans and the cap, and closes the earlier open question about running behind a proxy. Documented in the chat-server README, including the two ways to misconfigure it.

- Payload responses are validated too (`apps/chat-server/src/payloadClient.ts`, Zod schemas for rooms and bans). A response that does not match is rejected whole, so the sync logs the field names (never the values) and the Redis cache keeps its last good copy instead of being overwritten. - HTTP hardening for the chat-server (`apps/chat-server/src/app.ts`, split out of `index.ts` as `createApp()` so it can be tested): Helmet security headers on every Express answer, and a rate limit on `GET /rooms`, the one public unauthenticated endpoint (60 per minute per client IP, `429 { error: "rate_limited" }` plus `Retry-After`, `RateLimit` header on every answer; `/health` is not limited). The client IP comes from `app.set("trust proxy", TRUST_PROXY_HOPS)`, the same setting the socket code uses, so a forged `X-Forwarded-For` buys no fresh allowance (tested with 0 hops and with 1 hop, including a client-made-up leftmost entry). The count is per process, like the per-IP connection cap. Written test-first (11 tests); 6 deliberate bugs (no Helmet, trust everything, no trust setting, limit on all routes, wrong body, no headers) were each caught; the 4 real-browser e2e tests pass (CORS and sockets unaffected) and the live dev server returns the headers. - Message history (`apps/chat-server/src/history.ts`, `useChat.ts` on the web side): every message is appended to a per-room Redis list (newest `ROOM_HISTORY_SIZE`, default 50, at most 200; expires `ROOM_HISTORY_TTL_SECONDS` after the last message, default 1 hour, at most 7 days) in one transaction, before it is delivered live. The `room:join` ack now carries the room's history, read after the guest has joined, so nothing sent in between is missed; the web client merges it by message id (no duplicates, sorted by time, other rooms ignored), which also covers messages missed during a reconnect. A Redis failure costs only the history entry, never the live message, and an unreadable history never blocks a join. Entries are validated with Zod when read. Written test-first (history module, socket and client tests, a reconnect scenario in the real-browser suite: 147 chat-server, 59 web, 6 e2e tests pass); 10 deliberate bugs were tried and 9 caught (the tenth, throwing inside the reader's own try block, is an equivalent change). Open design questions, to be reviewed: messages are readable by anyone who joins a public room; there is no way to delete a single message (a ban now replaces all of its author's, see the next bullet); history is shared across nodes through Redis but the room-capacity lock is still per process.
- Bans now reach guests who are already connected and what they said (`enforceBans` in `socket.ts`, wired in `index.ts` through `startBansSync`; `redactMessagesFrom` in `history.ts`). Found while designing this: a banned guest who was already connected kept chatting, because bans were only checked at connection time. After every ban sync (all active bans, so it also heals races): connected banned guests of the node are sent `kicked { reason: "banned" }` and disconnected; in every room the history entries from the banned IP hashes are replaced, in one Lua script inside Redis, by placeholders with no text, nickname or guest id; the room gets `message:redacted { roomSlug, ids, guestIds }` and clients swap those messages for a red "This user was banned" (en/da/de), including older messages by the same guest that the history no longer holds. History entries now carry the sender's IP hash (server only, never sent to clients; entries from before this change have none and are not shown). A message still being recorded when the ban lands is dropped and redacted. On the client a placeholder in the history overrides a live copy, and live duplicates are ignored by id. Written test-first (chat-server 173 tests, web 74 tests, 7 real-browser scenarios including one where a banned guest is removed while another watches her message turn into the placeholder on screen, and a later joiner never sees the text); 16 deliberate bugs were tried and 15 caught (the survivor, a redundant exclusion of the removed guest from the notice, was removed instead); the Lua script was also run against a real Redis (order, expiry, nothing left behind, idempotent, tolerates a corrupt entry). Limits: up to one sync interval of delay (30 s by default); a replaced message stays replaced after a temporary ban expires; the stored hash is a salted IP hash, so someone with the salt could test an address against it, but cannot read addresses from it. Also fixed along the way: the e2e Payload login now times out after 30 seconds instead of hanging when the admin app is wedged.

### Not yet done

- `apps/chat-server` socket logic still missing: capacity enforcement across multiple nodes (joins to limited rooms are serialized per room by an in-process lock and the per-IP connection cap is counted per process; a Redis-side counter is needed before running more than one instance).
- Presence cost: every join, leave and disconnect sends the full member list to everyone in the room, so traffic grows roughly with the square of the room size. Fine for small rooms; very large or unlimited rooms need counts or deltas instead.
- Payload schema changes are applied by dev-mode push only; there are no migrations yet, so the `maxMembers` change (now optional) needs a migration before any real deployment.
- `apps/web` gaps: no typing/unread indicators, no mobile-specific layout work beyond Tailwind defaults.
- `apps/chat-server` and `apps/web` have no ESLint setup (type checking and Prettier only).
- CI has no dependency audit step yet (the 9 known `braces` highs would fail a plain `npm audit`), and no deployment pipeline.
- No tests for the Redis-backed sync jobs (`rooms.ts`, `payloadClient.ts`) or the HTTP routes yet; the socket tests mock those layers.
- No project-specific tests added beyond fixing the template's existing Vitest/Playwright scaffolding to match the real collections.
